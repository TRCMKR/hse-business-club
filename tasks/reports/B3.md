## Решение по денормализации

- `listing_author_id uuid NOT NULL` копируется в `Apply` из `ListingReader.GetListing` (автор
  публикации не меняется, ARCHITECTURE §1 правило 3). Индекс
  `applications_listing_author_idx (listing_author_id, status, created_at DESC)`.
- По нему без межконтекстных вызовов: права в `Get`/`Accept`/`Decline`/`Withdraw` и список
  «полученные» (`ListReceived` → `ListByListingAuthor`).
- `ListByListing` проверяет автора через порт (`GetListing`), а не по строкам откликов — при нуле
  откликов иначе нечего проверить.
- Межсхемных FK нет: `listing_id`, `listing_author_id`, `applicant_id` — просто `uuid`
  (ARCHITECTURE §1 правило 2; в SPEC §3 у `applications` указаны `REFERENCES` — см. «Дыры»).

## Транзакции и гонки

- Переходы (`Accept`/`Decline`/`Withdraw`) — `Repo.Update`: одна транзакция `db.WithTx`,
  `GetForUpdate` (row lock) → функция сервиса (права + `domain.Transition`) → `UpdateStatus`,
  либо без записи при `noop` (`updated_at` не меняется). Сервис не видит pgx: в интерфейсе
  `service.Repository` — `Update` с замыканием; `GetForUpdate`/`UpdateStatus` с `pgx.Tx`, как в
  задании, есть у `Repo` и используются внутри `Update`.
- Повторный отклик ловится partial unique index: параллельный второй `INSERT` ждёт коммита первого
  и получает `23505` → `KindConflict`. Отдельной проверки «есть ли отклик» перед вставкой нет
  (она была бы гонкой).
- `decided_at` ставится только для accept/decline (UTC, микросекунды), для withdraw — `NULL`
  (как в proto: «null для pending и withdrawn»). `updated_at = now()` в БД.

## Отступления

1. **403 vs 404 для второй стороны.** Порт и задание: «actor = автор публикации, иначе
   KindNotFound». SPEC §2.3 одновременно требует `PermissionDenied` для accept/decline не автором и
   withdraw не откликнувшимся, а 404 — только если пользователь «ни автор публикации, ни
   откликнувшийся». Реализовано согласованное прочтение SPEC (источник истины):
   посторонний → `KindNotFound` «Отклик не найден»; другая сторона (откликнувшийся на
   accept/decline, автор на withdraw) → `KindForbidden` «Недостаточно прав». Сигнатуры порта не
   менялись; комментарий в `applications.go` («иначе KindNotFound») не правил — он вне зоны,
   стоит уточнить (см. «Дыры»).
2. **Порядок проверок в переходах:** сначала права, затем машина состояний. Т. е. откликнувшийся,
   пытающийся accept отозванный отклик, получит 403, а не 400.
3. **Валидация `message`:** обрезаются пробелы по краям (`strings.TrimSpace`), сохраняется
   обрезанное; длина в символах (рунах). Только пробелы → ошибка. Проверка — до обращения к
   `ListingReader`.
4. **Фильтр статуса:** неизвестное значение → `KindValidation` (field `status`) «Статус отклика:
   неизвестное значение». Подписи для `status` в SPEC §2.4 нет; BFF маппит proto-enum и сюда
   неизвестное значение передавать не должен — это страховка.
5. **Тексты, которых нет в SPEC:** «Отклик не найден» (KindNotFound для отклика), «Недостаточно прав»
   (KindForbidden — текст из задания). `KindNotFound` для публикации отдаёт `ListingReader` (B5) как есть.
6. **Где лежат интеграционные тесты сервиса.** Гонка `Apply` и решений на реальной БД — в
   `postgres/service_integration_test.go` (package `postgres_test`), а не в `service/`: оба пакета
   работают со схемой `applications`, `dbtest.Migrate` делает `DROP SCHEMA`, а `go test ./...`
   гоняет пакеты параллельно — при тестах в двух пакетах они ломали друг друга (наблюдалось).
   Итог: все DB-тесты контекста в одном пакете, последовательно.
7. Сортировки дополнены `id DESC` для полного порядка при равных `created_at`.

## Дыры и вопросы к документам

- **SPEC §3 vs ARCHITECTURE §1 правило 2:** в DDL `applications` есть `REFERENCES listings(id)` /
  `users(id)`, а межсхемные FK запрещены. Сделано по ARCHITECTURE (без FK); SPEC §3 стоит поправить
  (и добавить туда `listing_author_id` с индексом).
- **404/403 для второй стороны** (отступление 1): комментарии порта в `applications.go` и
  ARCHITECTURE §2 («иначе KindNotFound») расходятся с SPEC §2.3 (403 для участника, 404 для
  постороннего). Предлагаю поправить комментарий порта: «посторонний — KindNotFound, другая
  сторона — KindForbidden». B4/B5 e2e: проверять 403 для откликнувшегося на accept.
- В SPEC §2.4 нет подписи для фильтра `status` и текстов «не найдено» для отклика / «недостаточно
  прав» — выбраны «Отклик не найден», «Недостаточно прав».
- `make test-integration` гоняет пакеты параллельно: если B1/B2 тоже разнесут DB-тесты одного
  контекста по нескольким пакетам, будут те же конфликты на `DROP SCHEMA` (см. отступление 6).
