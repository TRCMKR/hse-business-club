### Решения

- **Загрузка окружения в Makefile.** Каждая цель экспортирует `.env.deploy` (`set -a; . ./.env.deploy; set +a`).
  `DOCKERHUB_USERNAME` и `DOCKERHUB_PASSWORD` берутся по порядку: из окружения (login-zsh
  уже экспортирует их из `~/.zprofile`), из `.env.deploy` или из `~/.zprofile` через
  `zsh -c '. ~/.zprofile; print -r -- "$VAR"'`. Из профиля читаются только эти две
  переменные, поэтому `/bin/sh` не исполняет zsh-профиль, а Linux без zsh тоже работает.
  Если переменных нет, цель падает с понятной ошибкой. Все три пути проверены.
- **Подвох Kamal (Thor):** `-c` должен стоять после подкоманды. `kamal -c file config`
  молча печатает usage с кодом 0, а `kamal config -c file` работает правильно. В Makefile
  используется второй вариант, в README есть предупреждение.
- **`kamal remove` не используется.** Он вызывает `proxy remove`. Есть защита: прокси не
  удаляется, если на сервере есть другие приложения. Но `deploy-remove` всё равно
  выполняет только `app remove` (front, затем back) и `accessory remove all`.
- **Сборка из рабочего дерева.** Явный `builder.context` отключает git-clone Kamal, поэтому
  в образ попадают и незакоммиченные правки, а к тегу добавляется `_uncommitted_…`.
  Это описано в README.
- **Cookie и X-Forwarded-Proto.** В `front/server/utils/auth-cookie.ts` флаг `secure`
  зависит только от `NUXT_COOKIE_SECURE`. `getRequestURL` в BFF-прокси используется только
  для query, публичный origin фронту не нужен. Доверять `X-Forwarded-Proto` не требуется,
  Dockerfile не правился.
- **Сеть.** Kamal 2.11 запускает и приложения, и accessories с `--network kamal` (проверено
  в исходниках гема и в собранных аргументах конфига). Алиасы задаются через
  `options.network-alias`.
- **Порядок `kamal setup`** (по исходникам 2.11): bootstrap → build/push → proxy boot
  (для бэка пропускается, у роли нет прокси) → `accessory boot all` → `app boot` с ожиданием
  healthy до `deploy_timeout`. Если бэк не дождался базы, контейнер падает и перезапускается
  (`--restart unless-stopped`), а поллер Kamal повторяет проверку до таймаута.
  Hook для миграций не нужен, B6 переносит их в entrypoint (`goose up` → `exec hbc`).
- **kamal-proxy на сервере** — v0.9.2, это ровно `MINIMUM_VERSION` Kamal 2.11, поэтому
  `proxy reboot` не понадобится.

## Что проверено локально

- `make deploy-config` выдаёт `kamal config: ok` для обоих конфигов. `kamal config -c …`
  с реальными секретами: версия, образы, accessories, logging собираются корректно. Через
  Ruby API проверено, что все секреты непустые, DSN имеет вид
  `postgres://hbc:<48 hex>@hbc-db:5432/hbc?sslmode=disable`, у back `running_proxy?=false`,
  у front `true`, у accessories `--network kamal`.
- `make -n deploy` показывает загрузку env и затем `kamal deploy -c config/deploy.back.yml && kamal deploy -c config/deploy.front.yml`.
- Без `DOCKERHUB_*` в окружении переменные подхватываются из `~/.zprofile`. Если нет ни
  окружения, ни профиля, выводится ошибка `DOCKERHUB_USERNAME / DOCKERHUB_PASSWORD are not set`.
- Кросс-сборка `docker buildx build --platform linux/amd64 --load` (builder `desktop-linux`, QEMU, холодный кэш):

  | Образ | Время | Где время | Размер |
  |---|---|---|---|
  | back | 655 с | ~420 с скачивание `golang:1.25-alpine` amd64 (медленная сеть), `go mod download` 144 с, `go build` 229 с | 36,5 МБ |
  | front | 247 с | `npm ci` 118 с, `nuxt build` 116 с | 174 МБ |

  Фронт под QEMU собирается быстро (~4 мин), поэтому альтернатива (`builder.remote`, GHA) не
  нужна. Бинарь бэка amd64 запускается и сообщает об отсутствующих env. Контейнер фронта amd64
  с `NUXT_MOCK_API=true` отдаёт `/login` 200 через 3 с, RSS под QEMU 142 МиБ (нативно
  будет меньше).
- После проверки удалены образы `hbc-*:amd64-check` и выполнены `docker builder prune -af`
  (освобождено 2,0 ГБ) и `docker image prune -f` (117 МБ dangling).
- `make lint test` / `npm run …` не запускались: код не менялся.

## Ресурсы сервера (замер 2026-10-20)

- **RAM:** 961 МБ total, **available 469 МБ**, swap 512 МБ (занято 203). Чужие контейнеры
  занимают около 144 МБ (amnezia-awg2 38, fs-front 60, trcmkr-front 36, kamal-proxy 8).
- **Наш стенд, ожидаемое потребление:** back ~30–40, front ~80–120, postgres ~40–60
  (shared_buffers 32 МБ), minio ~80–100. Итого **~250–320 МБ** из 469. Во время деплоя
  фронта старый и новый контейнеры работают одновременно, это ещё +100 МБ на десятки секунд.
- **Лимиты** (`--memory`): 160 + 256 + 160 + 160 = 736 МБ. Это потолки, а не резерв, они
  защищают соседей от утечки в нашем контейнере. Риск: если все четыре контейнера дойдут
  до потолка, хост уйдёт в swap. Самый вероятный пик — обработка фото больших размеров
  (до 8000×8000 по SPEC) в бэке: такое фото может не уложиться в 160 МБ, тогда сработает
  OOM-kill и рестарт контейнера. Обычные фото с телефона укладываются.
- **Диск:** свободно 1,8 ГБ. Наши образы: back 37 МБ, front 174 МБ, postgres ~280 МБ,
  minio ~160 МБ, итого **~650 МБ**, плюс данные (десятки МБ). `retain_containers: 2`
  и лимит логов. Останется около 1,1 ГБ. На сервере ещё 1,04 ГБ reclaimable-образов чужих
  приложений, их не трогал.
