Ветка `task/B6`. Сделаны все пункты задания. Мигратора в коде больше нет: схему создаёт
только goose по файлам `back/migrations/`. В контейнере миграции применяет entrypoint,
локально их применяет `make migration-*`, в тестах — библиотека goose (`dbtest`).
ARCHITECTURE и SPEC не менялись: они уже были обновлены под B6 и совпадают с кодом.

репозиториев и раньше обращались к таблицам по полным именам, их менять не пришлось.

`app.New` теперь считает, что схема уже есть; `/readyz` проверяет только `pool.Ping` и
`blob.Ping`. Advisory-lock сида и проверка, что таблица пуста, не менялись.
`cmd/hbc/main.go` правок не потребовал.

## Как работает entrypoint

`back/Dockerfile`:
- в builder-стадии ставится `goose` командой `go install …/cmd/goose@$(go list -m … goose/v3)`.
  Версия берётся из `go.mod` (v3.27.0). Сборка только с драйвером Postgres (теги `no_mysql
  no_sqlite3 …`);
- в runtime-образ копируются `/usr/local/bin/goose`, `/app/migrations/` и
  `/usr/local/bin/docker-entrypoint.sh`. Пользователь не root (10001), alpine 3.20.
  Образ весит **46,5 МБ** (раньше ≈ 35 МБ);
- `ENTRYPOINT ["/usr/local/bin/docker-entrypoint.sh"]`.

`back/docker-entrypoint.sh` (POSIX sh):
1. если `POSTGRES_DSN` не задан — выход с ошибкой;
2. ждёт БД: раз в секунду запускает `goose … status`, всего `MIGRATIONS_WAIT_SECONDS`
   попыток (по умолчанию 30). Если БД так и не ответила — выводит ошибку goose и выходит с
   кодом 1;
3. выполняет `goose -dir /app/migrations postgres "$POSTGRES_DSN" up`. Если миграция упала —
   выход с ошибкой, `hbc` не запускается;
4. `exec /usr/local/bin/hbc "$@"`: приложение становится PID 1 и получает SIGTERM (graceful
   shutdown при `docker restart` проверен).

Проверено:
- образ на пустой БД применил три миграции, загрузил сид, `/readyz` = `{"db":"ok","blob":"ok"}`;
- повторный старт: `goose: no migrations to run. current version: 20261020000003`, в логе
  `demo data skipped`;
- недоступная БД: выход с кодом 1 и сообщением `entrypoint: database is not reachable after Ns`.

`docker-compose*.yaml` не менялись.

## Make-цели (`back/Makefile`)

Сделаны по образцу bot-aller и matcher-back: `MIGRATION_FOLDER = $(CURDIR)/migrations`,
цели `migration-create name=…` (`goose create … sql`, имя с timestamp), `migration-up`,
`migration-down`, `migration-status`. DSN берётся из `POSTGRES_DSN`: `.env` или окружение,
по умолчанию `TEST_POSTGRES_DSN` (тестовый compose, :5433). goose запускается через
`go run -tags '…' github.com/pressly/goose/v3/cmd/goose@$(GOOSE_VERSION)`, версия — из `go.mod`.
Ставить goose глобально не нужно. Старый вариант `migration-create ctx=… name=…` удалён.

## Тесты

`internal/platform/db/dbtest`:
- `MigrationsDir()` — абсолютный путь к `back/migrations`, вычисляется через `runtime.Caller`,
  а не от cwd;
- `Up(ctx, pool)` — `goose.NewProvider(DialectPostgres, …, os.DirFS(dir))` + `Up`. Вместо
  `goose.SetBaseFS` и глобального goose используется Provider: у него нет глобального
  состояния, а результат тот же;
- `Reset(ctx, pool)` — `DROP SCHEMA users, listings, applications CASCADE` и `DROP TABLE
  public.goose_db_version`;
- `Migrate(t, pool)` — `Reset` + `Up`, в cleanup снова `Reset`.

**Сериализация пакетов (дополнение к заданию).** Раньше у каждого контекста была своя схема
и своя таблица версий, и `go test ./...` мог гонять пакеты параллельно. Теперь база, схемы и
таблица версий общие: `Reset` одного пакета ломал бы тесты другого. Поэтому `dbtest.Pool`
(и e2e `TestMain` через `dbtest.Lock`) один раз на процесс берёт `pg_advisory_lock` на
отдельном соединении и держит его до выхода процесса. Пакеты, которые ходят в Postgres,
выполняются по очереди, остальные — параллельно, как и раньше. Время `make test-all` почти
не изменилось: ≈ 1,5 мин.

Изменения в тестах:
- `platform/db`: `TestMigrations` проверяет, что повторный up ничего не делает, что применено
  3 версии, что таблицы на месте, что `DownTo(0)` удаляет все три схемы и что после этого up
  восстанавливает их. `TestWithTx` теперь работает на своей временной схеме `b0_test`;
- тесты репозиториев (`users`, `listings`, `applications`) переведены на `dbtest.Migrate` и
  `dbtest.Up`, проверки таблицы версий — на `public.goose_db_version`;
- e2e `TestMain`: `dbtest.Lock` → `Reset` → `Up`.

## Что учесть

- **Старые локальные тома.** В БД, созданной до B6, таблицы уже есть, но версии лежат в
  `<ctx>.goose_db_version`. Новый `goose up` упадёт с `relation "users.users" already exists`,
  и back не стартует. После merge нужен один раз `make reset && make up` в корне. Это касается
  и запущенного сейчас стека `hbc` на main. Тестовое окружение живёт в tmpfs, его это не касается.
- **I3 / Kamal.** Хуки для миграций не нужны: их применяет entrypoint образа перед `hbc`,
  ему нужен только `POSTGRES_DSN`. Если контейнер не стартует, причина видна в логе
  (`kamal app logs`): строки goose идут до JSON-логов приложения. Образ стал ≈ 46 МБ. Если
  когда-нибудь будет несколько реплик, стартующих одновременно, стоит подумать о блокировке
  миграций: goose CLI сам её не берёт. Для одного сервера это неважно.
- В entrypoint можно настроить `MIGRATIONS_WAIT_SECONDS` (по умолчанию 30) и `MIGRATIONS_DIR`
  (по умолчанию `/app/migrations`).

## Итерация 1 (ревью)

- В entrypoint на время ожидания БД добавлен `trap 'exit 143' TERM INT`. Пауза между
  попытками сделана через `sleep 1 & wait $!`, чтобы сигнал срабатывал сразу. Результат:
  `docker stop` контейнера без БД занимает около 0 с, код выхода 143.
- После первой неудачной попытки выводится `entrypoint: waiting for database (up to Ns)`.
- Если сервер отклонил подключение (`password authentication failed`, `does not exist`,
  `FATAL`), entrypoint сразу выходит с кодом 1 и печатает ошибку. Исключение — `FATAL: the
  database system is starting up / shutting down`: это значит, что Postgres ещё стартует, и
  ожидание продолжается. Проверено с неверным паролем и с несуществующей базой.
- В `back/README.md` упомянута переменная `MIGRATIONS_DIR`. В корневом README §Запуск
  добавлена строка про `make reset && make up` для старых томов.
- Повторная проверка: `docker build ./back` и `make reset && make up && make smoke` через
  override (`-p hbc-b6`) — 16/16. После проверки выполнен `down -v`, образы `:b6` удалены.
