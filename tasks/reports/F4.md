# Отчёт F4 — Отклики

Ветка `task/F4`. Экраны откликов, бейдж «Отклики» в навигации, тесты.

## Что сделано

1. **`/listings/:id/applications`** (`app/pages/listings/[id]/applications.tsx`). Видит только автор.
   - Карточки `ApplicationCard` в режиме `incoming`. Для pending есть «Принять» (сразу, без
     подтверждения) и «Отклонить» (через `ConfirmDialog`, tone danger).
   - Фильтр по статусу чипами, значение в query `status` (`pending|accepted|declined|withdrawn`,
     без параметра = «Все»; неизвестное значение тоже = «Все»).
   - В заголовке название публикации (`listings.get`), ссылка «К публикации».
   - Пустой список: «Откликов пока нет». Пусто при фильтре: «Нет откликов со статусом «…»» и
     кнопка «Показать все».
   - 403 (не автор): toast «Отклики на публикацию видит только её автор» и `router.replace`
     на `/listings/:id`. Редирект делается на клиенте в `onMounted`: при SSR-редиректе toast
     пропал бы. Пока идёт редирект, SSR показывает состояние «Недостаточно прав».
   - 404 по публикации или откликам: `createError(404, 'Публикация не найдена')`.
2. **`/me/applications`** (`app/pages/me/applications.tsx`).
   - `Tabs` «Отправленные» / «Полученные», вкладка в query `tab`: `received` или ничего (по
     умолчанию `sent`). Смена вкладки сбрасывает фильтр статуса.
   - На вкладке «Полученные» счётчик = значение бейджа.
   - Фильтр статуса на обеих вкладках.
   - Отправленные: карточки `outgoing` (публикация со ссылкой на детали, автор, мой текст,
     статус) и «Отозвать» с подтверждением для pending.
   - Полученные: карточки `incoming` с «Принять» / «Отклонить» и ссылкой на публикацию.
   - Пустые состояния. Отправленные: «Вы ещё не откликались» → «Перейти в ленту».
     Полученные: «Откликов пока нет» → «Мои публикации». При фильтре: «Нет откликов со
     статусом …».
3. **Бейдж** (`app/composables/useApplicationsBadge.ts`). Заглушка F0 заменена, сигнатура
   `useApplicationsBadge()` → `Ref<number>` (`ComputedRef`) сохранена. Header и tab-bar не
   менялись.
4. После успешного действия отклик сразу заменяется в списке ответом сервера, и кнопки
   пропадают. Затем делается `refresh()` списка.

Обработка ошибок в `ApplicationActions`: любая ошибка показывается toast'ом через
`getErrorMessage`. На 400 («Решение по отклику уже принято»), 403, 404 и 409 дополнительно
эмитится `stale`, и страница перезагружает список. Сетевая ошибка даёт только toast.
Идемпотентный повтор (сервер отвечает 200 с текущим состоянием) обрабатывается как успех.

## Как работает бейдж и его инвалидация

- Состояние хранится в `useState('applications-badge')` и общее для всех вызовов (header,
  tab-bar, страницы): `{ userId, count, fetchedAt }`. Текущий запрос и номер последовательности
  лежат в `WeakMap`, ключ — `nuxtApp`; это не пользовательские данные.
- `useApplicationsBadgeControl()` возвращает `{ count, refresh({ force? }) }`. `refresh` делает
  `GET /v1/me/applications/received?status=APPLICATION_STATUS_PENDING`, `count = items.length`.
  - Без `force` запроса нет, если прошлый начался меньше 30 с назад или ещё идёт: параллельные
    вызовы из header и tab-bar дают один запрос.
  - С `force` запрос идёт всегда. Ответ более старого запроса отбрасывается по номеру
    последовательности.
  - Если `auth.user.id` не совпадает с `state.userId`, счётчик сразу обнуляется и
    перезагружается принудительно. Так число прошлого пользователя не показывается после
    входа или выхода, хотя `clearNuxtData()` не трогает `useState`. `count` дополнительно
    сверяет `userId`. Без пользователя бейдж = 0 и запроса нет.
  - Ошибка запроса оставляет прежнее число.
  - В SSR `refresh` ничего не делает: SSR и первый клиентский рендер дают 0, расхождения
    гидрации нет.
- `useApplicationsBadge()` (его вызывают nav-компоненты) в `onMounted` вызывает
  `refresh()` и подписывается на смену пользователя и `route.path`, с тем же ограничением
  раз в 30 с. Пользователь появляется после входа: layout `auth` без навигации сменяется на
  `default`, nav монтируется, и счётчик загружается.
- После accept и decline (и после ошибки) `ApplicationActions` вызывает
  `refresh({ force: true })`. Withdraw число полученных pending не меняет, поэтому бейдж не
  трогает.

## Проверка

- `npm run lint` и `npm run test` зелёные: 17 файлов, 176 тестов. `npm run build` проходит.
- Dev-сервер `NUXT_MOCK_API=true npm run dev -- --port 3104`, проверка через curl с
  cookie-сессиями демо-аккаунтов (SSR-HTML и API):
  - Анна: `received?status=PENDING` = 1 (Борис), SSR `/me/applications?tab=received`
    показывает pending с «Принять» / «Отклонить». Accept от Бориса → 403. Accept от Анны →
    `ACCEPTED`, повтор → 200, decline после этого → 400 «Решение по отклику уже принято».
    Pending после этого = 0.
  - Борис: в «Отправленных» FinTrack со статусом «Принят», кнопки «Отозвать» нет.
  - Вера: в «Отправленных» отклик на Volunteer Hub со статусом «Отозван», без кнопок.
  - `/listings/<id>/applications?status=accepted` от Анны: активный чип, «Нет откликов со
    статусом «Принятые»». От Бориса: состояние «Недостаточно прав» (дальше клиентский
    редирект). Несуществующий id → 404 «Публикация не найдена».
- **Не проверено в браузере:** инструмента управления браузером в сессии не было. Клиентское
  поведение (бейдж «1» → «0» после клика «Принять», toast, редирект на 403) покрыто
  компонентными тестами, а не ручным прогоном.

## Что не сделано / ограничения

- Ручной браузерный прогон критерия «бейдж 1 → 0» не сделан (см. выше).
- Бейдж не обновляется push'ем: новые отклики появятся при навигации, не чаще раза в 30 с.
- Счётчики по статусам в чипах фильтра не показываются: в API нет агрегатов для этих списков,
  только `ListingStats` у публикации.

## Правки в общих зонах

- `front/tests/applications-*.test.ts` — новые файлы в общей папке тестов F0. Существующие
  файлы не менялись.
- Общие компоненты F0, nav, сервисы и mock не менялись.
- Стили страниц лежат в `components/applications/page.module.css`, а не рядом со страницами,
  чтобы не выходить из зоны владения.

## Замечания к документам

- В README и отчёте F0 сказано «не храните пользовательские данные в `useState`», а задача F4
  предлагает «общий `useState`» для бейджа. Решение: state привязан к `userId` и сам
  сбрасывается при смене пользователя. Стоит уточнить формулировку в README фронта.
- SPEC и задача не задают формат значения query `status`. Выбраны короткие значения
  (`?status=pending`), не enum-имена API.
- Вкладка по умолчанию на `/me/applications` не задана. Выбраны «Отправленные» (первая
  вкладка), на «Полученных» есть счётчик pending.
- Конвенция F0 «`throw createError(404)` в setup» не упоминает, что в `async setup()` без
  `<script setup>` все композаблы (`useHead`, `onMounted` и т. п.) нужно вызвать до первого
  `await`: после него контекст Nuxt теряется, и SSR падает с 500. Полезно добавить в README
  фронта для F1–F5.
- Окружение: во время работы диск заполнился до 0 байт, потому что несколько worktree
  одновременно ставили `node_modules` (~630 МБ каждый). Первый `npm ci` упал с ENOSPC,
  частичная установка удалена, повторная `npm ci --prefer-offline` прошла.
