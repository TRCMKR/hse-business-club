## Домен (`domain`)

- `NormalizeCreate(CreateParams)` / `NormalizeUpdate(kind, UpdateParams)` — trim строк, длины в
  рунах (`utf8.RuneCountInString`), первая ошибка — `apperr.Validation(field, msg)`, `Field` — имя
  поля proto (`title`, `looking_for`, …). Порядок проверок: kind → title → description →
  looking_for → tags → stage → compensation.
- `NormalizeTags` — trim, пустые отбрасываются, ≤ 40 рун, дубли без учёта регистра → ошибка,
  ≤ 10 после отбрасывания пустых; порядок сохраняется; результат никогда не `nil`.
- `NormalizeFilter` — `Page 0 → 1`, `Limit 0 → 20` (дефолты для незаданных полей proto), иначе
  `page ≥ 1`, `limit 1..50`; `query` trim, ≤ 100 рун; `kind` — `""`/startup/vacancy.
- `ValidateStatusFilter` (для `ListByAuthor`): `""`/active/closed.
- `CheckAuthor` (KindForbidden «Недостаточно прав»), `CanEdit` (KindPrecondition «Публикация
  закрыта»), `NeedsClose` (closed → no-op), `ErrNotFound()` (KindNotFound «Публикация не найдена»),
  `ErrNotActive` — внутренний sentinel репозитория (не `apperr`, наружу не выходит).

Сообщения (подписи из SPEC §2.4):

| Поле | Сообщение |

## Сервис

- `Create` — нормализация → `repo.Create`.
- `Get` — любой статус; `GetMany` — пустой вход → пустая map без запроса.
- `ListActive` — `NormalizeFilter` → `Page{Items, Total, Page, Limit}` (с применёнными дефолтами).
- `Update`: порядок проверок `NotFound → Forbidden → Precondition («Публикация закрыта») → Validation`
  (чужой на закрытой получает 403, а не 400; валидация по сохранённому `kind`). Запись условная
  (`WHERE status='active'`); если публикацию закрыли между чтением и записью — повторное чтение
  и `KindPrecondition`.
- `Close`: `NotFound → Forbidden`; закрытая — возвращается как есть, без записи (`closed_at` не
  меняется); гонка с параллельным закрытием — тоже возвращает текущее состояние.

## SQL-особенности

- Схема `listings`, таблица по SPEC §3, но `author_id uuid NOT NULL` **без** FK (ARCHITECTURE §1).
  Индексы `listings_feed_idx (status, created_at DESC)`, `listings_author_idx (author_id, created_at DESC)`.
  `stage` в БД — `NULL` для vacancy (`NULLIF($, '')` на запись, `COALESCE(stage,'')` на чтение).
- Запросы с явной схемой `listings.listings`: миграции идут с `search_path=listings`, а рабочий пул —
  с дефолтным `search_path`.
- Сортировка `created_at DESC, id DESC` — `id` как tie-breaker для стабильной пагинации.
- `ListActive` — два запроса (`count(*)` и страница `LIMIT/OFFSET`) в одной транзакции
  `REPEATABLE READ READ ONLY`: total согласован с items и корректен для страницы за концом
  (с `COUNT(*) OVER()` на пустой странице total не получить). При `total = 0` второй запрос не выполняется.
- Поиск: `title ILIKE $2 ESCAPE '\' OR description ILIKE $2 ESCAPE '\'`, где
  `$2 = '%' || EscapeLike(query) || '%'` собирается в Go; экранируются `\`, `%`, `_`.
  Фильтры через `($1 = '' OR kind = $1)` — один текст запроса на все комбинации.
- `Update`/`Close` — `UPDATE … WHERE id=$1 AND status='active' RETURNING …`; `Close` ставит
  `status='closed', closed_at=now(), updated_at=now()`. `Update` меняет `updated_at`, `kind` не трогает.
- `GetMany` — `WHERE id = ANY($1)`; списки возвращают `[]` вместо `nil`, `Tags` — тоже никогда не `nil`.

## Отступления и решения

1. **Строки обрезаются (`TrimSpace`)** у `title`, `description`, `looking_for`, `compensation`, `query`,
   длины считаются в рунах после trim. SPEC явно пишет «после trim» только для tags/skills; для
   остальных полей это моё решение (иначе «   » проходит как looking_for). Фронту стоит делать так же.
2. **Сообщения для случаев, которых нет в SPEC** — придуманы в стиле «Подпись: …» (таблица выше):
   неизвестная стадия у startup, неизвестный `kind`, недопустимый `status` в `ListByAuthor`
   (для `status` подписи в таблице SPEC нет — взял «Статус»). Через proto-enum'ы BFF эти случаи
   практически недостижимы.
3. **Порядок `Forbidden` раньше `Precondition`** в `Update`/`Close` и валидация после них — SPEC порядок
   не задаёт.
4. **Интеграционный тест сервиса лежит в пакете `postgres`** (`service_integration_test.go`): все
   интеграционные тесты listings используют одну схему `listings`, а `go test ./...` гоняет пакеты
   параллельно — тесты из двух пакетов мешали бы друг другу.
5. **`internal/app/app.go` не правил** (вне зоны), хотя комментарий там говорит «B1–B3 add theirs
   here»: регистрация `postgres.Migrator` и сборка сервиса — на B4/B5 (сниппет выше).
6. Субагенты не поднимались — объём небольшой, всё сделано последовательно.
