## Решения и отклонения

- **Logout отзывает всю семью**, а не только предъявленный токен. Logout завершает вход целиком, а не одну ротацию, и это строже. SPEC говорит «отзывает refresh», ARCHITECTURE — «идемпотентно», и то и другое соблюдено. Если нужно строго по одному токену, это одна строка в `RevokeRefresh`.
- **Пустой `refresh_token` у logout → 200**, у refresh → 401. Logout идемпотентен (SPEC §2.3: «неизвестный → 200»).
- **`DeleteExpired` удаляет все истёкшие** токены пользователя, отозванные тоже. Для истёкшего токена обнаружение повторного использования не нужно: он отклоняется по сроку.
- **Ротация упирается в `SELECT … FOR UPDATE`.** Две одновременные ротации одного токена: вторая видит `revoked_at` и отзывает семью. Это намеренно, такова семантика обнаружения повторов. Важно для фронта, см. ниже.
- `bff.Deps.AccessTTL` добавлен вместо расширения интерфейса `auth.Issuer`. Порт `Issuer` из ARCHITECTURE не тронут.
- `service.New` получил новый позиционный аргумент `tokens` и опции. В ARCHITECTURE сигнатура конструктора не зафиксирована.
- Фейки в unit-тестах пока рукописные (`fakeTokens`, методы refresh в `fakeUsers`). B8 заменит их на mockery.

## Для фронта (F9)

- `POST /v1/auth/register`, `/login`, `/refresh` → 200:
  ```json
  {"accessToken":"eyJ…","refreshToken":"<43 символа base64url>","accessExpiresIn":900,"user":{…User…}}
  ```
  Ровно четыре ключа. `accessExpiresIn` — секунды (по умолчанию 900). Refresh живёт 30 дней (`REFRESH_TTL=720h`), его срок в ответе не передаётся.
- `POST /v1/auth/refresh {"refreshToken":"…"}`, без Authorization. Каждый вызов отдаёт **новый** refresh, старый сразу отзывается.
  - Ошибка: 401 `{"code":16,"message":"Сессия истекла","details":[]}`.
  - Когда возникает: токен пустой, неизвестный, истёкший, отозванный (после logout), повторно использованный, длиннее 128 символов, или пользователь удалён.
- **Повторное использование** уже ротированного refresh отзывает всю семью, то есть новый refresh этого входа тоже умирает. Отсюда: конкурентные refresh одного токена (две вкладки или параллельные SSR-запросы) убивают сессию. На стороне Nitro нужно дедуплицировать refresh, один in-flight на токен.
- `POST /v1/auth/logout {"refreshToken":"…"}`, без Authorization → всегда 200 `{}`: пустой, неизвестный и повторный тоже. Отзывает весь вход (семью). Access остаётся валидным до своего `exp`: он stateless.
- Истёкший или невалидный access → 401 «Требуется вход». Отличить от refresh-ошибки можно по тексту.
- Другие входы (устройства) того же пользователя logout и отзыв семьи не затрагивают.
